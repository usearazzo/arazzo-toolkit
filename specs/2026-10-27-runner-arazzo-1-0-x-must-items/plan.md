The message names the parameter and the location it was given, e.g. `Parameter "petId" has location "body", which is not one of path, query, header, cookie, querystring`. ## Group 2 — #127: reject an unreadable `successCriteria` before the request

4. In `packages/runner/src/executor/StepExecutor.ts`, add a public method `assertSuccessCriteria(step)` that checks a step's `successCriteria` is absent or a list of Criterion Objects. It throws `ResolverError` with `reason: 'malformed-criteria'` (present but not a list) or `reason: 'malformed-criterion'` (an entry that is not a Criterion Object), with `target: 'successCriteria'` and the step's scope. This is the shape `ActionResolver#criteriaMet` uses for an action, which sets `target: 'criteria'`, the name of that field. It is public for the same reason `evaluateCriteria` is: the workflow executor needs it for steps that target a `workflowId`. Call it in `execute()` before parameters and the request body are resolved, so it precedes any request.
5. In `evaluateCriteria`, drop the `isCriterionElement` skip and the non-array `return true`, since step execution now reaches it only with a readable list. Absent `successCriteria` still succeeds, and the TSDoc says why.
6. In `packages/runner/src/executor/WorkflowExecutor.ts`, call `stepExecutor.forDocument(document).assertSuccessCriteria(step)` for a step that targets a `workflowId`, before the sub-workflow runs. That is the same `StepExecutor` derivation the executor already uses to call `evaluateCriteria` after the sub-run, so the check has one owner.
7. Tests: in `packages/runner/test/executor/StepExecutor.ts`, a step whose only `successCriteria` entry is not a Criterion Object, and a step mixing one readable and one unreadable entry, both reject with `malformed-criterion` and send no request. A scalar `successCriteria` rejects with `malformed-criteria`. In `packages/runner/test/executor/WorkflowExecutor.ts`, a `workflowId` step with an unreadable `successCriteria` rejects before the sub-workflow's first request. Every new spec title in this group contains `malformed successCriteria`, so validation check 4's `--grep` selects all of them.

## Group 3 — #117: merge workflow default actions by `name`

8. In `packages/runner/src/normalizer/ArazzoWorkflowNormalizer.ts`, replace the presence-keyed wholesale inheritance in `#inheritActionsToSteps` with a merge by `name`. The step's effective `onSuccess` is its own actions in order, followed by each workflow `successActions` entry whose `name` none of the step's actions carries, in workflow order. Do the same for `onFailure` / `failureActions`, independently. A step with no list, or with `[]`, gets every workflow action. Within the step's list and within the workflow's list alike, the first action with a given `name` wins. An entry without a readable string `name` (including one that is not an action object) neither overrides nor is overridden: it keeps its place, and a workflow one is appended unless that same element is already in the step's list. A step whose `onSuccess` / `onFailure` is present but not a list is left untouched, as today, so the executor still reports it. Keep the workflow's action elements shared, not copied, so retry budgets keyed by element identity behave as today. Keep the pass idempotent for a workflow reached again through the registry cache: a second run must not append the workflow actions twice. The `hasKey` presence test no longer provides that, so it comes from the name and element-identity checks above. Rewrite the method's TSDoc to quote the specification sentence, state the merge, and replace the paragraph explaining idempotence through `hasKey`.
9. In `packages/runner/test/normalizer/ArazzoWorkflowNormalizer.ts` (`context('action inheritance')`), replace the specs that assert wholesale override and `onSuccess: []` removal with specs for: a step action replacing the same-named workflow action; workflow actions the step does not name appended after the step's own, in order; `onSuccess: []` inheriting all; success and failure merging independently; a duplicate `name` resolving first-wins, both within the step's list and within the workflow's; an entry without a `name` kept in place and not appended twice; a non-list `onSuccess` left untouched; inherited entries being the workflow's own elements (`strictEqual`, not copies); normalizing twice producing the same lists; and a `$components`-referenced action merging by its dereferenced `name`. These specs live in `context('action inheritance')`, which validation check 7's `--grep` selects.
10. In `packages/runner/test/executor/WorkflowExecutor.ts`, add a run-level spec whose title contains `merged default actions`: a workflow with a failure action `end` and a step with its own differently named `onFailure` `goto` runs the step's `goto` first, while a failing step whose own action does not match falls through to the inherited `end`. Update existing WorkflowExecutor specs that relied on wholesale override, if any.
