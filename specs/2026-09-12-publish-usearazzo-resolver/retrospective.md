# Phase 1 Retrospective — Publish @usearazzo/resolver

Curated from the `## Spec deviations` section of the implementation PR (#157) and the review findings applied on that PR before merge.

## Deviations from the spec

- `requirements.md` § Decisions "Bundle element variants take a ParseResultElement only" and `plan.md` Group 1 tasks 6–9: `bundleArazzoElement` and `bundleOpenAPIElement` were dropped by maintainer decision during implementation; only whole documents bundle, mirroring `@speclynx/apidom-reference`, which has no `bundleApiDOM`. The surface is ten functions and sixteen new public names, and `validation.md` checks 1, 2 and 7 were applied to that reduced surface (the README table names ten functions, the `.d.ts` grep matches 16 names).
- `requirements.md` § Decisions "One element-context module per document kind" and `plan.md` tasks 2 and 3: the extraction was implemented, then reverted by maintainer decision in favour of inlining the base-URI and media-type derivation in the four `*Element` functions, since each context module had only two callers once the bundle element variants were gone.
- `plan.md` tasks 4 and 5: `resolveArazzoElement` / `resolveOpenAPIElement` cannot forward a seeded `dereference.refSet` to `resolveApiDOM`; the upstream resolve strategies deep-merge a fresh `ReferenceSet` over it (ramda `mergeDeepRight`), which strips the prototype and crashes the resolution. All four resolve functions now drop `dereference.refSet` before calling upstream and document the option as ignored.
- `plan.md` tasks 4 and 5: the plan specified the document-kind check only for the URI variants. The element variants as first implemented overwrote a caller-supplied `parse.mediaType`, accepted an OpenAPI parse result in `resolveArazzoElement`, and threw a raw upstream `TypeError` for a child element passed without `strategyOpts.parseResult` or `resolve.baseURI`. All three were fixed after review with regression tests; the root-reference shape for a child element (a wrapper around a copy of the child, keyed by the root URI) is documented rather than reshaped, because the upstream strategies traverse `rootRef.value` and a re-keyed set could serve either the child or the whole document, not both.
- `plan.md` task 9: the resolve tests asserted only the set's size, URIs and root kind. Review added the assertions the operation's contract actually promises: the root parse result still contains its `$ref`s, the input element is the root reference itself, and a seeded `dereference.refSet` is ignored.
- `plan.md` tasks 6 and 7: the bundle defaults were specified "as in task 4 plus `bundle.strategies`", which copied `resolve.strategies` and a `dereference` block (including a `sourceDescriptions` switch) into options the upstream bundle pipeline never reads. Trimmed after review to the bundle strategies plus the shared resolvers and parsers. The resolve and bundle defaults now spread the dereference defaults instead of re-declaring them.
- `requirements.md` § Out of Scope "No runner changes" and `plan.md` task 11: `packages/runner/package.json` had its exact `@usearazzo/resolver` pin bumped to `1.0.1-alpha.2`; without it `npm install` cannot match the workspace package and falls back to the registry (404). The runner and validator `@usearazzo/parser` pins were bumped too after review: left at `1.0.1-alpha.0`, they pulled a nested registry parser copy so the runner loaded two parser versions and neither suite exercised the workspace parser. `release.yml` runs `lerna version --no-private`, which never rewrites the private packages' exact pins, so this recurs on every release.
- `plan.md` task 11: the lockfile refresh also removed the nested registry copies of `@usearazzo/parser@1.0.1-alpha.0` under `packages/resolver/node_modules` (and, after the pin bump above, under `packages/runner` and `packages/validator`), which the stale pins had been pulling in place of the workspace package.
- `plan.md` task 12: the README "repoints references" wording was wrong for Arazzo bundling, which embeds the external JSON Schema resource under `components.inputs` with its `$id` and leaves the `$ref` as written; corrected in a fix-up commit. The `*Element` rows also lost the `dereference.strategyOpts.parseResult` precondition for child elements in the rewrite; restored after review. `specs/tech-stack.md` § Data and Storage pointed at the README § Options section the rewrite removed; repointed to the website reference.
- `plan.md` task 13: "list the resolver as published" was reworded after review to "publishable", because the manual `npm publish` happens after the PR merges and the constitution would have been false in between. `.claude/CLAUDE.md` carried the same claim plus a stale "resolver is private" note and an entry-point list missing resolve and bundle; both were outside the plan and fixed on the PR.
- `plan.md` task 14 and `validation.md` check 21: the ` ✅` lifecycle marker was applied on the PR as planned, while the phase goal ("on npm") is only met by the manual publish after merge. Review questioned marking the phase complete before the publish is verified, and the marker was removed again by maintainer decision; it is appended once `npm view @usearazzo/resolver` confirms the release. The spec never said which event the marker follows.

## Root cause

The spec was scaffolded by mirroring the shape of the existing dereference module across the two new operations instead of reading the upstream entry module for each one. That is how the bundle defaults inherited strategies the bundle pipeline never reads, how the resolve element variants assumed the dereference contract for seeding a `ReferenceSet`, how the bundle element variants assumed an upstream `bundleApiDOM` that does not exist, and how the element variants ended up specified with fewer checks than the URI variants. The tests followed the same pattern and asserted the shape of the result rather than the contract of the operation.

On the manifest and publish side, `tech-stack.md` did not surface that the private packages pin the public ones with exact versions outside the `lerna version --no-private` flow, so the plan scoped the pin bump to the resolver alone. The plan also treated "published" as a state the PR achieves, while the first publish is a manual step after merge, so both the constitution wording and the roadmap lifecycle marker ran ahead of the operational deliverable.

## Lesson for future specs

- When a phase wraps an `@speclynx/apidom-reference` operation, the spec must cite the upstream entry module (`resolve/index.mjs`, `bundle/index.mjs`, `dereference/index.mjs`) and list the option keys it reads; the operation's `defaultOptions` carry only those keys, never a copy of a sibling operation's defaults.
- Before planning an `*Element` variant, confirm the upstream exposes an ApiDOM-level entry point (`dereferenceApiDOM`, `resolveApiDOM`; there is no `bundleApiDOM`). No entry point, no variant.
- Specify an `*Element` variant with the same checks as its URI variant: the document-kind check and error class, the precedence between caller options (`resolve.baseURI`, `parse.mediaType`) and derived values, and the behaviour for a child element passed without `strategyOpts.parseResult`. Name the shape of the result for a child element explicitly.
- Tests for a resolve-style operation assert the contract, not the shape: the input is left untouched, nothing is dereferenced, and the input element is the root reference. A shape-only suite passes against an implementation that dereferences in place.
- A manifest task that changes a public package's version must bump every workspace consumer's exact pin of that package (private packages sit outside `lerna version --no-private`) and run the consumer suites, so no nested registry copy shadows the workspace link.
- A phase whose goal includes "on npm" must state which event the ` ✅` marker follows (merge, or the manual publish verified with `npm view`) and word the constitution for the state that is true at merge time.

## Promotion candidate

yes — "the private packages pin the public ones with exact versions outside `lerna version --no-private`, so every public version bump needs a manual pin bump in `runner` and `validator`" is a load-bearing release invariant for `specs/tech-stack.md`.
